## Design decisions made explicit (the spec left these open)

- **`ZL-JJOB-` prefix, not `ZL-JOB-`** for Jewellery Job codes —
  deliberately distinct from Phase 3's existing Diamond Job prefix
  (which the master plan's own example text happens to share), so a
  Diamond Job and a Jewellery Job can never produce an identical
  human-readable code or be confused for one another.
- **Metal is fungible/weight-based; Phase 3 diamonds stay discrete/
  piece-based — and they resolve completely differently.** Metal issued
  to a job drains a shared weighted-average cost pool
  (`remainingWipCost`, metal-only); each diamond resolves directly by
  its own individually-costed `costAtIssue`, never via that shared pool
  or any ratio. Both still debit the same Jewellery WIP account at issue
  time (correct at the ledger level) — this is an application-level
  cost-tracking distinction, not an accounting one.
- **"Other material" cost is job-costing-display-only, never posted to
  the ledger** — directly required by the master plan's "do not falsely
  present manual material as fully inventory-traced" instruction, since
  no real stock/source account backs it.
- **Karigar labour AND Karigar-added-material payable both reuse the
  existing Accounts Payable control account** (`2000`, by `partyId`),
  same reasoning as Phase 3's labour payable — no new liability account
  needed.
- **Normal process loss stays absorbed into finished jewellery's
  carrying cost by default** (matching Phase 3's diamond weight-loss
  treatment); an Owner may explicitly classify a specific loss as
  "abnormal" (mandatory reason) to carve its cost out to Business
  Expenses instead.
- **Completion requires BOTH the metal gap to reach zero AND every
  issued diamond to be resolved** — a job cannot complete with metal
  fully reconciled but a diamond still unresolved (verified live — see
  below).
- **`jewelleryMedia.ts` is a deliberately separate, duplicated storage
  module**, not shared with Phase 3's `diamondMedia.ts`, to avoid any
  risk of regressing already-verified, committed Phase 3 code. Identical
  security properties throughout.

## Self-caught design bugs (before any code compiled or ran)

- Initially planned to combine metal + diamond cost into one shared WIP
  pool drained by weight ratio during receipts — caught before writing
  `receiveFinishedJewellery`: this would have applied a shared-pool ratio
  to individually-costed diamonds, which is wrong. Fixed by tracking
  `remainingWipCost` as metal-only; diamonds always resolve by their own
  exact cost.
- Initially planned to include `otherMaterialCost` in the "Dr Finished
  Jewellery Inventory" journal line — caught before finalizing: there is
  no real account to credit against it, which would have produced an
  unbalanced voucher. Fixed by excluding it from the accounting voucher
  entirely (display-only figure on `FinishedJewellery.otherMaterialCost`).

### Iteration notes (found and fixed during this verification pass)

Building the Playwright script itself surfaced three real, worth-fixing
issues, none of which were caught by the 121 unit tests (which don't
touch the browser DOM):

1. **Missing `htmlFor`/`id` pairing and `aria-label`s on several plain
   `<select>` controls** in `MetalPurchaseForm.tsx`,
   `ReceiveFinishedForm.tsx`, `MetalStockTab.tsx`, and
   `MetalPuritySettingsPanel.tsx` — visually labelled but not
   programmatically associated, an accessibility gap. Fixed by adding
   proper `id`/`htmlFor` pairs or `aria-label`s to every one (verified:
   `tsc`/`eslint`/`vitest` still clean afterward).
2. A test-harness-only race in the verification script itself (not a
   product bug): submitting three party-creation forms back-to-back
   without reloading between them could let a stale "Party added."
   success message from a *previous* submission satisfy the next
   submission's wait-for-success check, silently skipping the actual
   third submission. Fixed in the script by reloading the page fresh
   before each submission.
3. A test-harness selector-index mismatch (also not a product bug): one
   form's purity `<select>` has a leading "Choose purity…" placeholder
   option and another's does not, so the "same" numeric index pointed at
   two different purities across the two forms — caused an early,
   correctly-behaving "not enough stock" rejection from the real posting
   engine (proving the negative-stock guard works) rather than a product
   defect. Fixed in the script by using the correct index for each form.

### 3. Other-material cost allocation

Implemented as: proportional-by-finished-gross-weight, recalculated
across the job's **entire output history** every time a new output is
created (prior receipts' outputs get their stored `otherMaterialCost`/
`totalCost` retroactively corrected in the same database transaction).
Automated coverage (`src/lib/jewellery/posting.test.ts`,
"other-material cost allocation across outputs", 6 tests): one output;
multiple outputs in one receipt; partial receipt then final receipt
(retroactive recalculation of the first receipt's earlier output(s));
unequal output weights; the rounding remainder always lands somewhere
and the total allocated always equals the total issued cost exactly;
a job that receives zero outputs leaves the cost unallocated rather
than crashing; other-material cost is confirmed to never create a
journal-entry line (it stays display-only). Manual example verified
against the automated test's own numbers: job issues ₹90.00 other-
material cost; first receipt has one 30g output → that output gets the
full ₹90.00; a later receipt adds a 60g output → recalculation splits
₹90.00 across 30g+60g by gross weight (1:2 ratio) → first output's
`otherMaterialCost` is retroactively corrected down to ₹30.00, the new
output gets ₹60.00, and 30.00 + 60.00 = 90.00 exactly.

Live-verified in the same real browser run: the mixed-purity job's

from every journal entry posted for this job (each receipt's posting

### Real bugs found and fixed this pass

1. **Prisma interactive-transaction timeout (5000ms default) exceeded
   under real network latency.** The new per-purity/per-line/per-output
   posting logic makes enough sequential round trips against the real
   remote Supabase Postgres instance that `receiveFinishedJewelleryAction`
   failed with `PrismaClientKnownRequestError [P2028]: A commit cannot
   be executed on an expired transaction. The timeout for this
   transaction was 5000 ms, however 5198–6242 ms passed...` (confirmed
   from the dev server's own error log, not assumed). The same class of
   failure also hit `issueMaterialsAction` once enough diamonds had
   accumulated to issue in one call. **Fixed** by passing
   `{ timeout: 20000 }` to `prisma.$transaction` for
   `receiveFinishedJewelleryAction`, `issueMaterialsAction`, and
   (defensively, same risk profile) `cancelJewelleryJobAction` in
   `src/app/actions/jewellery.ts`. No other call site in the codebase
   already customized this timeout, confirming this was genuinely new
   ground, not a missed existing convention.

2. **A finished output's own metal purity was validated against the
   Metal/Purity master at large, not against what the job actually
   issued** — and this pass's own CONSUMED_OUT generalization (crediting
   each output's own real purity, to fix the "always the first-issued
   purity" limitation) made that a real Metal Stock ledger corruption
   risk, not just an input-hygiene gap: an output recorded in a purity
   the job never issued would silently drain a completely unrelated
   purity's real stock balance. **Directly confirmed live**, not just by
   reasoning about the code: during this pass's own testing, a finished
   output was accidentally recorded at `10K` (the Metal/Purity master's
   first entry by seed order — a form-default artifact, since the
   output-purity dropdown was, at the time, unrestricted) even though
   this test session never purchased or issued any 10K metal at all.
   The Metal Stock tab's live totals (screenshot `b05-metal-purchases.png`,
   captured mid-run) showed the exact corruption in real numbers:
   `GOLD · 10K` with **gross 0.000g, fine −2.085g, cost −₹31,202.88** —
   a real purity's balance driven negative by metal it never actually
   held. **Fixed** in `src/lib/jewellery/posting.ts`: an output's
   `purityId` is now validated against the job's own issued-purity
   snapshot map (the same set return/scrap lines are restricted to),
   rejected with `PostingError` if it names a purity the job never
   issued, and its fine weight is computed from that job's own fineness
   *snapshot* rather than a fresh Metal/Purity master lookup (so a later
   master edit can't retroactively change an already-posted output's
   fine weight either). `src/components/jewellery/ReceiveFinishedForm.tsx`
   was updated to match: the output "Metal type"/"Final purity"
   dropdowns are now restricted to `issuedPurities`, exactly like the
   return/scrap dropdowns, so the UI can no longer offer a choice the
   server will reject. Added a dedicated regression test ("rejects a
   finished output recorded in a purity that was never issued to this
   job") asserting both the rejection and that the un-issued purity's
   Metal Stock ledger receives zero movements of any kind. Re-verified
   the live database after this fix: the corrupted `10K` movements were
   already gone (they belonged to now-deleted temporary jobs from
   cleanup), and a fresh read-only query confirmed zero
   `MetalStockMovement` rows remain and the 7 real seeded `MetalPurity`
   master rows are untouched.

3. **A completed Jewellery Job's detail page kept showing "Pending with
   Karigar"** for the same gap-based fine-weight figure that Phase 3's
   own diamond-job detail page already relabels to "Weight loss (final)"
   once a job completes. Confirmed live: the same completed job
   (screenshot `b08-final-receipt.png`) showed "Pending with Karigar:
   4.413g" even though the job's status read `Completed` and that
   4.413g was in fact the already-recognized, already-absorbed process
   loss — reading as if metal were still outstanding with the Karigar
   on a job that was actually fully resolved. **Fixed** by adding the
   same completed-job relabeling Phase 3 already has:
   `getJewelleryJobDetail` (`src/lib/jewellery/reports.ts`) now exposes
   `finalMetalLossFineWeight` (the same gap figure, only populated once
   `status === "COMPLETED"`), and `JobDetailView.tsx` swaps the label to
   "Metal loss (final)" and that value once the job is completed —
   mirroring `src/components/diamond/JobDetailView.tsx`'s existing
   `finalWeightLossCarat`/`isCompleted` pattern exactly. Confirmed the
   job list view's compact "X g pending" row text was already correct
   as-is (Phase 3's own diamond job list shows the identical
   unconditional "X ct pending" in its compact row — a deliberate,
   consistent simplification at that density, not a gap); only the
   detail view needed the fix.
